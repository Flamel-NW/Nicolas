Condition C interaction protocol:

The task text may ask for complete updated module contents. For condition C,
that requirement is overridden by this protocol.

Use the condition C tools to apply the requested changes to the task workspace:
1. Fact discovery: use `semantic_query` first for trusted module structure,
   affected modules, dependents, callers, and effect-chain facts. Use SQL only
   when a required trusted fact is not covered by a semantic query.
2. Narrow source read: use `read_nico_section` for the smallest relevant source
   section. Use `read_file` only as a last-resort full-file fallback.
3. Required edits: use `edit_nico` to apply every source change to the
   workspace. `edit_nico` accepts either `.nico` workspace paths or DB source
   paths ending in `.rs`; `.rs` paths are normalized to the matching `.nico`
   workspace file. Prefer structural ops (`insert_interface_item`,
   `replace_interface_item`, `update_interface_function_effects`,
   `update_module_imports`, `update_module_effects`,
   `insert_implementation_item`, `replace_implementation_function`) for
   interface items, interface function effects, module-level imports,
   module-level effects, and implementation functions. Use exact-anchor ops
   only for local replacements.
   Do not use broad `replace_text` edits for module-level `imports [...]` or
   module-level `effects [...]`; use `update_module_imports` and
   `update_module_effects` so function-level effects are not matched by
   mistake.
   Do not run routine dry-run previews. Apply structural ops directly, and
   apply exact-anchor edits directly when you have just read the source section
   containing the exact anchor. Dry-run is only for genuinely uncertain anchors
   that cannot be made safe with a narrow source read.
   For propagation tasks, call `semantic_query affected_modules` first and use
   the returned `source_edit_plan`. The older `source_effect_update_plan` is
   only a module-effect subset; prefer `source_edit_plan` when both are
   present. Rows marked `required_edit=true` are required workspace source
   edits. For type or constructor shape changes, required `checks_examples`
   and `call_sites` categories mean every stale example or call site must be
   updated or explicitly verified unchanged. Rows marked `required_edit=false`
   or `no_op_edit=forbidden` only forbid edits for that row's effect action;
   they do not cancel required example, check, or call-site updates from type
   dependency rows. Do not treat DB `propagated_effects` as a substitute for
   updating `.nico` source when `source_edit_plan` requires a source change.
   For a provider type shape change, first read the provider `surface`,
   `checks`, and `implementation` sections, then apply one provider batch that
   covers imports/effects, interface type/function surface, checks/examples,
   and implementation. Existing implementation items must be updated, not
   inserted: use exact-anchor `replace_text` for existing structs/enums/types
   and `replace_implementation_function` for existing functions.
4. Retry rule: if an edit fails, retry only the failed file/edit after reading
   the narrowest relevant section or using the returned nearest anchors. Do not
   repeat the full fact discovery pass. For implementation exact-anchor edits,
   do not invent or assume an anchor such as a `use` line that may not exist;
   use exact text copied from the narrow source section you just read, or use a
   structural implementation-function edit when changing a whole function.
5. Stop rule: once all `source_edit_plan required_edit=true` edits have been
   applied and all required rows' completion gates have been satisfied, do at
   most one necessary validation pass, then immediately stop editing and
   produce the compact final answer. Do not run no-change edits,
   dry-run previews, comment/doc-only edits, formatting cleanup, broad
   re-validation loops, or repeated readbacks after the required edits are
   already applied. Do not use remaining turns for doc/comment cleanup,
   duplicate-removal attempts, or formatting repairs after a source edit batch
   has reported success. The edit tool performs source structure validation; if
   it reports success, do not keep editing just to reformat the source.
6. Do not present complete updated module contents in the final answer.

Final answer format:

Use exactly these four final sections. Do not use an "Analysis" or "Plan"
section as the final answer. Markdown headings are tolerated by the harness,
but the preferred final answer labels are the exact labels below.

Summary:
- List the modules changed and the semantic purpose of each change.

Evidence:
- List the trusted queries, source sections, or tool results used to decide the
  affected modules and call/effect propagation.

Boundary/effects check:
- State any dependency-direction or effect-propagation decisions, including
  modules intentionally left unchanged.

Validation status:
- State whether the workspace edits were applied through `edit_nico`.
- If no source edits were applied, explicitly say that no workspace source
  changes were applied.
