# E4 Golden Reference — suspend_user effects 声明

## 任务

在 `user.profile_service` 中添加新函数 `suspend_user(id: UserId) -> ()`。该函数需要通过 `user.store.mark_deactivated()` 将用户状态设为停用，通过 `audit.log.record()` 记录操作，并使 cache 中该用户的条目失效。要求正确列出并声明 `suspend_user` 的所有 effects，不遗漏、不虚报。

## 标准答案

### 1. `user.profile_service`（主要改动）

#### spec.interface 新增函数

```
fn suspend_user(id: UserId) -> ()
  effects [db.read, db.write, audit.write]
  // db.read：通过 user.store.mark_deactivated()，该函数先读再写（effects [db.read, db.write]）
  // db.write：同上
  // audit.write：通过 audit.log.record()
  // reads_clock 说明见下方
```

#### effects 关键辨析

**`db.read` 必须声明**（高频漏报点）：

`user.store.mark_deactivated()` 的 effects 声明为 `[db.read, db.write]`（先读取现有档案，再写回更新后状态）。因此调用它的函数必须继承这两个 effects，不能只声明 `db.write`。

**`reads_clock` 是否声明，取决于 cache 失效策略的选择：**

| cache 失效策略 | 对应调用 | reads_clock |
|--------------|---------|-------------|
| 删除条目（推荐） | `kv::delete(key)` | **不需要**（delete 无 effects）|
| 覆写为哨兵值 | `kv::set(key, "", CacheTtlPolicy::Fixed(CacheTtl(0)))` | **需要**（set 有 reads_clock）|

**推荐策略**：调用 `kv::delete()`（语义上更清晰：停用 = 驱逐 cache），effects 为 `[db.read, db.write, audit.write]`，不含 reads_clock。

**若选择 `kv::set()` 覆写**：effects 为 `[reads_clock, db.read, db.write, audit.write]`，两种选择均可接受，前提是 effects 声明与实现一致。

**`user.profile_service` 模块级 effects 不变**：当前模块级 `effects [reads_clock, db.read, db.write, audit.write]` 已包含所有可能出现的 effects，无论选择哪种 cache 策略，模块级声明均不需要修改。

---

#### implementation rust 新函数（骨架）

```rust
/// Suspend the user account identified by `id`.
///
/// Marks the profile as deactivated in persistent storage and invalidates
/// any cache entry. Records a `UserDeactivated` audit event.
///
/// # Effects
/// - `db.read`:   via `user.store::mark_deactivated()`.
/// - `db.write`:  via `user.store::mark_deactivated()`.
/// - `audit.write`: via `audit.log::record()`.
pub fn suspend_user(_id: UserId) {
    store::mark_deactivated(super::types::new_user_id(0)); // skeleton: placeholder id
    let key = CacheKey(String::new());
    kv::delete(key); // invalidate cache; pure, no reads_clock
    let event = log::new_event(
        AuditActor::System,
        ProfileAuditAction::UserDeactivated,
        super::types::new_user_id(0),
    );
    log::record(event);
}
```

---

### 2. 不需要修改的模块

| 模块 | 理由 |
|------|------|
| `user.store` | `mark_deactivated` 已存在且 effects 声明完整，无需修改 |
| `audit.log` | `UserDeactivated` variant 已在 `ProfileAuditAction` 中定义，无需新增 |
| 其他模块 | 均不受 profile_service 内部新增函数影响 |

---

### 不应出现的 effects 声明

| 错误 effects | 原因 |
|-------------|------|
| 仅声明 `db.write`，遗漏 `db.read` | mark_deactivated 同时有 db.read（需先读取档案） |
| 新增 `reads_config` | suspend_user 不经过 config.loader |
| 新增 `metrics.write` | suspend_user 不调用 metrics.recorder（注意：user.admin_service 的 force_deactivate 会记录 metrics，但 user.profile_service 的 suspend_user 不应复制此行为，除非任务明确要求） |
| 新增 `db.read` 仅因"需要先查 profile"的推测 | effects 来自实际调用链，不来自推测；应基于 mark_deactivated 的声明 effects，而非重新分析底层实现 |

---

### 与 `user.admin_service.force_deactivate` 的对比

`user.admin_service.force_deactivate` 也执行停用操作，但额外调用 `metrics.recorder.record()`，因此有 `metrics.write` effect。`user.profile_service.suspend_user` 是纯业务层停用，不涉及 metrics 上报，不应引入 `metrics.write`。

## 评分 Rubric

### task_success（0 / 0.5 / 1）

**1.0（满分）** 需同时满足：

- `suspend_user` 的 effects 声明包含 `db.read`（来自 mark_deactivated）
- `suspend_user` 的 effects 声明包含 `db.write`（来自 mark_deactivated）
- `suspend_user` 的 effects 声明包含 `audit.write`（来自 audit.log.record）
- 对 `reads_clock` 的取舍有明确立场（使用 delete 则不声明；使用 set 则声明），且声明与描述的实现一致
- 未虚报 `metrics.write`、`reads_config` 等不相关 effects
- `user.profile_service` 模块级 effects 不变（已包含所有可能 effects）

**0.5（部分完成）** 适用于：

- 正确声明 `db.write` 和 `audit.write`，但遗漏 `db.read`
- effects 声明与描述的实现不一致（如说用 delete 但又声明了 reads_clock）
- 正确添加了函数但未考虑 audit event 的 action 类型（使用了不存在的 variant）

**0.0**：

- 只声明 `audit.write`，漏掉 db effects
- 声明了 4+ 个错误的不相关 effects
- 未能添加函数到正确模块

### compile_rate

- `cargo build` 通过（exit 0）
- 若使用了不存在的 `ProfileAuditAction` variant：编译报未找到变体错误
- 若 `CacheKey` 构造方式与当前实现不符：编译报错

### boundary_violation

- 若 `suspend_user` 实现中直接调用了 `std::time::SystemTime::now()` 而不通过 `time.clock::now()`：标记为 `boundary_violation`（违反 Restricted Rust 约束）

## 实验注意事项

**条件 A（raw Rust）：** LLM 需阅读 `user/store.rs` 中 `mark_deactivated` 的函数文档注释以推断 effects（注释说明"先读后写"）；需阅读 `audit/log.rs` 确认 `UserDeactivated` variant 已存在；需阅读 `cache/kv.rs` 的 `delete()` 函数注释确认其无 effects。

**条件 C（Semantic DB）：** 可查询 `trusted.functions WHERE module = 'user.store' AND name = 'mark_deactivated'` 直接获得 effects `[db.read, db.write]`。可查 `trusted.types WHERE module = 'audit.log' AND name = 'ProfileAuditAction'` 确认 `UserDeactivated` variant 已存在（通过 types repr 或 intent 字段）。可查 `trusted.functions WHERE module = 'cache.kv' AND name = 'delete'` 确认 delete 无 effects。

**条件 D（注解 Rust）：** `@nico-fn` 注解提供函数级 effects 声明，可快速查到 mark_deactivated 的 effects；`@nico-type` 注解列出枚举 variant（但 v0 注解可能不包含 variant 详情，需读 .rs 文件确认）。

**已知 LLM 行为风险：**

- **高频漏报 `db.read`**：直觉上"停用"是写操作，LLM 常只声明 `db.write`，忽视 mark_deactivated 先读后写的实现细节
- 盲目复制 `user.admin_service.force_deactivate` 的 effects（含 `metrics.write`），而 suspend_user 不需要 metrics
- 条件 A 下因无法直接获取 mark_deactivated 的 effects 声明，依赖函数名语义猜测（高风险）
- 条件 C/D 下可精确查到 effects，风险较低
