# E5 Golden Reference — cache hit/miss metrics 上报架构决策

## 任务

为 cache 的 hit/miss 情况添加 metrics 上报能力。在不违反禁止依赖方向的前提下，从以下三种方案中选择一种，给出明确选择并说明理由：

- **方案 A**：向 `cache.kv` 添加 `metrics.write` effect，在 `get()` 内部上报
- **方案 B**：新建中间层模块（如 `cache.metrics`）负责上报
- **方案 C**：由 `user.profile_service` 在外层调用 `cache.kv.get()` 后自行上报

## 标准答案

### 推荐方案：方案 A（cache.kv 内部上报）

**理由：**

1. **语义完整性**：hit/miss 信息在 `cache.kv.get()` 内部产生，上报应与产生位置同层。`cache.kv` 是唯一能精确感知 hit/miss 的边界。
2. **覆盖完整性**：`cache.kv` 被 3 个模块 import（`user.profile_service`、`session.service`、`rate.limiter`）。若在外层上报，只能覆盖一个调用方，其他两个的 cache 行为无法观测。
3. **符合 Nicolas 边界模块原则**：每种 effect 集中在边界模块，不散落于业务层。

---

### 方案 A 的实施变更

#### 1. `cache.kv`（新增 import + effect）

- `spec` 新增：`imports [metrics.recorder]`
- `spec.effects` 更新：`effects [reads_clock, metrics.write]`
- `spec.interface` 的 `fn get()` effects 更新：`effects [reads_clock, metrics.write]`
- implementation rust：
  - 新增 `use crate::metrics::recorder;`
  - `get()` 中在 hit/miss 路径各调用一次 `recorder::record(name, value)`

#### 2. effect 传播影响（必须识别）

添加 `metrics.write` 到 `cache.kv` 后，所有 import `cache.kv` 的模块都需要在 effects 声明中补充 `metrics.write`：

| 受影响模块 | 当前 effects | 更新后 effects |
|----------|------------|--------------|
| `user.profile_service` | `reads_clock, db.read, db.write, audit.write` | + `metrics.write` |
| `session.service` | `reads_clock, db.read, db.write, audit.write` | + `metrics.write` |
| `rate.limiter` | `reads_clock, metrics.write` | 已有（不变）|

注：`rate.limiter` 已声明 `metrics.write`（通过 import `metrics.recorder`），不受影响。

---

### 方案 B 的分析（不推荐）

**方案 B（新建 `cache.metrics` 模块）**：

- 要么 `cache.kv` 调用 `cache.metrics`（等同方案 A 加了一层中间层），要么 `cache.metrics` 包装 `cache.kv`（调用方需改用 `cache.metrics` 而非 `cache.kv`）
- **包装层方案**：需更改所有调用方（user.profile_service、session.service、rate.limiter）的 import，引入大量接口变更
- **中间层方案**：语义上无额外价值，但增加模块数量；在当前场景规模（13 模块）下属于过度分层
- **结论**：除非项目有明确的"观测层"架构规范，方案 B 不适合 v0 场景

---

### 方案 C 的分析（不推荐）

**方案 C（user.profile_service 外层上报）**：

- 只覆盖 profile service 的 cache 调用，session.service 和 rate.limiter 的 cache hit/miss 无法观测
- 需在 `user.profile_service` 新增 `import metrics.recorder`，并在每次调用 `kv::get()` 后检查返回值并上报
- 若未来 session.service 也需要 cache metrics，需再次重复类似改动
- **结论**：覆盖不完整，维护成本高；方案 A 的结构更清晰

---

### 完整改动清单（方案 A）

```
cache/kv.nico               spec：新增 imports [metrics.recorder]，effects 新增 metrics.write
                            spec.interface：fn get() effects 新增 metrics.write
                            implementation rust：new import + get() 中调用 recorder::record
user/profile_service.nico   spec.effects：新增 metrics.write
session/service.nico        spec.effects：新增 metrics.write（若未已声明）
```

注：rate.limiter 已有 metrics.write，不需要修改。

## 实验注意事项

**条件 A（raw Rust）：** LLM 需通过阅读所有模块的 use 语句推断"哪些模块 import 了 cache.kv"；推断 effect 传播需手动分析 import 图。依赖方向约束隐含在代码结构中，无显式注释。

**条件 C（Semantic DB）：** 可直接查询 `trusted.imports WHERE imported_module = 'cache.kv'` 获得所有 import cache.kv 的模块（user.profile_service、session.service、rate.limiter），精确评估方案 A 的 effect 传播影响。`trusted.propagated_effects` 可确认 rate.limiter 已有 metrics.write（方案 A 对其无影响）。

**条件 D（注解 Rust）：** `@nico-imports` 注解提供模块依赖关系，可识别 cache.kv 的直接依赖方；与条件 C 类似，但需手动整理。

**已知 LLM 行为风险：**

- **条件 A**：因无法快速查明"哪些模块 import cache.kv"，可能低估方案 A 的 effect 传播影响，或在不完整信息下错误推荐方案 C
- **条件 C/D**：可精确查到 3 个 cache.kv 依赖方，有利于做出有约束依据的决策
- 混淆"cache.kv 的 metrics"（命中率等）与"业务层的 metrics"（请求数等）——前者属于 cache 自身可观测性，后者属于业务逻辑监控
