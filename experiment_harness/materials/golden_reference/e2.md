# E2 Golden Reference — UserProfile 重命名为 UserRecord

## 任务

不修改任何函数行为。将 `user.types` 中的类型 `UserProfile` 重命名为 `UserRecord`，追踪所有直接和间接引用该类型名称的位置，并一致更新，确保 `cargo build` 通过。

## 标准答案

本任务是纯重命名（rename-only），不涉及任何语义变更。`compile_rate` 是最可靠的验证手段：任何遗漏的改动都会产生 Rust 编译错误。

---

### 1. `user.types`（定义处，必须改）

- `spec.interface` 中 `type UserProfile` → `type UserRecord`
- `spec.interface` 注释：`type UserRecord // 聚合类型：{ id: UserId, email: EmailAddress, status: UserStatus }`
- `fn new_profile(id, email, status) -> UserProfile` 返回类型 → `UserRecord`
- implementation rust：
  - `pub struct UserProfile` → `pub struct UserRecord`
  - `pub fn new_profile(...) -> UserProfile` → `-> UserRecord`
  - 函数体 `UserProfile { id, email, status }` → `UserRecord { id, email, status }`

---

### 2. `user.store`（直接依赖，必须改）

- `spec.interface` 函数注释中 `UserProfile` → `UserRecord`（如有引用）
- implementation rust：
  - `use super::types::{UserId, UserProfile, UserStatus}` → `UserRecord` 替换 `UserProfile`
  - `pub fn load_profile(_id: UserId) -> Option<UserProfile>` → `Option<UserRecord>`
  - `pub fn save_profile(_profile: UserProfile)` → `_profile: UserRecord`

---

### 3. `user.profile_service`（直接依赖，必须改）

- `spec.interface` 函数签名注释中 `UserProfile` → `UserRecord`（如有引用）
- implementation rust：
  - `use super::types::{UserId, UserProfile}` → `UserRecord`
  - `pub fn get_profile(_id: UserId) -> Option<UserProfile>` → `Option<UserRecord>`
  - `pub fn update_profile(_profile: UserProfile)` → `_profile: UserRecord`

---

### 4. `user.admin_service`（直接依赖，**容易漏报**）

- 任务描述的模块列表未提及 `user.admin_service`，但它 import 了 `user.types` 并直接使用 `UserProfile`：
  - `use super::types::{UserId, UserProfile}` → `UserRecord`
  - `pub fn list_users() -> Vec<UserProfile>` → `Vec<UserRecord>`
- **未更新此处会导致编译失败**，LLM 必须通过 import 图分析发现它

---

## 评分 Rubric

### task_success（0 / 0.5 / 1）

**1.0（满分）** 需同时满足：

- 正确重命名 `user.types` 中的定义（struct + function 返回类型）
- 正确更新 `user.store`（两处：load_profile 返回类型 + save_profile 参数类型）
- 正确更新 `user.profile_service`（两处）
- **正确更新 `user.admin_service`**（包括 import 和 list_users 返回类型）
- 正确判断 `audit.log` / `session.types` 等无需修改

**0.5（部分完成）** 适用于：

- 完成了 user.types / user.store / user.profile_service 的重命名，但遗漏了 `user.admin_service`
- 错误修改了不需要更新的模块（如修改了 audit.log）

**0.0**：

- 仅修改了 user.types 中的定义，未追踪任何调用侧
- 严重误报（更新了 5+ 个实际不包含 UserProfile 的模块）

### compile_rate

- `cargo build` 通过（exit 0）：要求所有引用处已更新
- **若遗漏 `user.admin_service`，cargo 会报错**：`use super::types::UserProfile` 找不到该名称

### boundary_violation

本任务为纯重命名，无依赖方向变化，通常不产生 boundary_violation。若 LLM 引入了新的 import（如 admin_service 新增了不必要的依赖），标记之。

## 实验注意事项

**条件 A（raw Rust）：** LLM 需在所有 13 个模块的 `.rs` 文件中搜索 `UserProfile` 关键字。骨架实现中引用主要出现在 use 语句和函数签名，数量有限，但 `user.admin_service` 在任务描述的"涉及模块"列表中未被提及，增加了遗漏风险。

**条件 C（Semantic DB）：** 可查询 `trusted.functions WHERE signature LIKE '%UserProfile%'` 或 `trusted.types WHERE name = 'UserProfile'`，直接定位所有使用该类型名称的函数签名。也可查 `trusted.imports WHERE imported_module = 'user.types'` 快速圈定可能受影响的模块集。

**条件 D（注解 Rust）：** 与条件 A 类似，依赖关键字搜索；`@nico-imports` 注解可辅助确认模块依赖关系，但不如 Semantic DB 精确。

**已知 LLM 行为风险：**

- **高概率漏报 `user.admin_service`**：任务描述的模块列表为 `user.types、user.store、audit.log、user.profile_service`，不包含 admin_service，LLM 倾向于只更新列表内的模块
- 条件 A 下若 LLM 仅从 intent 和 spec 推断依赖而不扫描实现代码，极易遗漏
- 过度更新：将 `UserStatus`（枚举名）也重命名（不应修改）
