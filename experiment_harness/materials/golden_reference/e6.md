# E6 Golden Reference — 添加 ProfileExported audit event

## 任务

在 `audit.log` 的 `ProfileAuditAction` 枚举中添加新 variant `ProfileExported`，并更新 `user.profile_service`，使其在导出用户 profile 时（新函数 `export_profile`）使用该新 event。要求不破坏 `record()` 函数的现有签名，不破坏任何现有的 audit event 记录行为。

## 标准答案

### 1. `audit.log`（添加 variant，additive 变更）

`ProfileAuditAction` 枚举新增 variant `ProfileExported`：

- `spec.interface` 中 `type ProfileAuditAction` 注释更新：
  ```
  type ProfileAuditAction
    // 操作枚举：ProfileViewed | ProfileUpdated | UserDeactivated | ProfileExported
  ```
- implementation rust：
  ```rust
  pub enum ProfileAuditAction {
      ProfileViewed,
      ProfileUpdated,
      UserDeactivated,
      ProfileExported,  // 新增
  }
  ```

**这是 additive 变更**：

- `new_event(actor, action, subject_id)` 签名**不变**（接受 `ProfileAuditAction`，新 variant 自动可用）
- `record(event)` 签名**不变**（接受 `AuditEvent`，结构不变）
- `AuditEvent` struct **不变**（仍为 `{actor, action, subject_id}`）
- 所有现有的 `ProfileViewed` / `ProfileUpdated` / `UserDeactivated` 调用**不受影响**

**变更类型**：枚举新增 variant 在 Rust 中是 breaking change（若有 exhaustive match），但在此场景中 `audit.log` 的 `record()` 内部实现是 `todo!()`，不存在 exhaustive pattern match，因此编译安全。

---

### 2. `user.profile_service`（新增函数）

新增函数 `export_profile(id: UserId) -> Option<UserProfile>`：

#### spec.interface 新增

```
fn export_profile(id: UserId) -> Option
  effects [db.read, audit.write]
  // db.read：通过 user.store.load_profile() 读取档案（仅读，不写）
  // audit.write：通过 audit.log.record() 记录 ProfileExported event
  // reads_clock：不需要（不走 cache read-through 路径，直接读 store）
```

注：若实现选择经过 cache（调用 `kv::get()`），则需加 `reads_clock`。标准答案选择直读 store（`export_profile` 的语义是"获取用户档案的导出副本"，可绕过 cache 直接从权威存储读取）。

#### implementation rust 新函数（骨架）

```rust
/// Export the user profile for the given ID.
///
/// Reads the profile directly from `user.store` (bypasses cache) and records
/// a `ProfileExported` audit event.
///
/// # Effects
/// - `db.read`:    via `user.store::load_profile()`.
/// - `audit.write`: via `audit.log::record()`.
pub fn export_profile(_id: UserId) -> Option<UserProfile> {
    let result = store::load_profile(super::types::new_user_id(0)); // skeleton
    let event = log::new_event(
        AuditActor::System,
        ProfileAuditAction::ProfileExported,
        super::types::new_user_id(0),
    );
    log::record(event);
    result
}
```

#### `user.profile_service` 模块级 effects

当前 `effects [reads_clock, db.read, db.write, audit.write]`。

- 若 `export_profile` 不调用 `kv::get()`（直读 store），模块级 effects **不变**（`db.read` 和 `audit.write` 已声明）
- 若选择经过 cache，`reads_clock` 已声明，也不变

---

### 3. 不需要修改的模块

| 模块 | 理由 |
|------|------|
| `user.store` | `load_profile` 已存在，无需修改 |
| `audit.log` 的其余接口 | `new_event()`、`record()` 签名不变 |
| 其他调用 `audit.log` 的模块 | `user.admin_service`、`session.service` 均不需要修改 |
| 其他所有模块 | 不受 profile_service 新函数影响 |

---

### additive 变更与 breaking 变更的辨析

这是 E6 的核心知识点：

| 变更类型 | 是否 breaking | 说明 |
|---------|-------------|------|
| 向 enum 新增 variant | 对 exhaustive match 是 breaking | 当前实现 `record()` 是 `todo!()`，无 exhaustive match，安全 |
| 修改 `new_event` / `record` 签名 | 是 | 不允许，题目明确要求不破坏现有签名 |
| 修改 `AuditEvent` struct | 取决于构造方式 | 不应修改，题目无此要求 |

在条件 C（Semantic DB）下，`trusted.functions` 可直接显示 `new_event` 和 `record` 的当前签名，LLM 可精确判断新 variant 是否 compatible。

## 评分 Rubric

### task_success（0 / 0.5 / 1）

**1.0（满分）** 需同时满足：

- 正确在 `audit.log` 的 `ProfileAuditAction` 枚举中新增 `ProfileExported` variant
- `new_event()` 和 `record()` 签名**未改变**
- 正确在 `user.profile_service` 中新增 `export_profile` 函数，使用 `ProfileAuditAction::ProfileExported`
- `export_profile` 的 effects 声明合理且与实现一致（至少含 `db.read` 和 `audit.write`）
- 未修改任何现有的 `ProfileViewed` / `ProfileUpdated` / `UserDeactivated` 调用

**0.5（部分完成）** 适用于：

- 正确添加了 variant，但 `user.profile_service` 中使用了错误的 variant 名（如 `ProfileExport` 或 `ExportProfile`）
- 正确更新了两个模块，但 effects 声明遗漏 `audit.write` 或声明了不必要的 effects
- 修改了 `new_event()` 或 `record()` 的签名（违反约束）

**0.0**：

- 未添加 variant 到 `ProfileAuditAction`
- 错误地修改了 `AuditEvent` struct（添加了 `export_data` 字段等）
- 未在 `user.profile_service` 中添加任何使用新 variant 的代码

### compile_rate

- `cargo build` 通过（exit 0）
- 若 `ProfileAuditAction::ProfileExported` 名称拼写错误：编译报 variant 未找到
- 若 `export_profile` 的返回类型与 `load_profile` 不匹配：编译报类型错误

### boundary_violation

- 若 `export_profile` 直接调用 `std::fs::write()` 或其他系统 API（而不通过 Nicolas 模块）：`boundary_violation`
- 若 `audit.log` 新增了 import `user.store` 等上层模块（方向反转）：`boundary_violation`

## 实验注意事项

**条件 A（raw Rust）：** LLM 需阅读 `audit/log.rs` 确认 `ProfileAuditAction` 的现有 variant 列表（`ProfileViewed`、`ProfileUpdated`、`UserDeactivated`）；需阅读 `user/profile_service.rs` 中 `new_event()` 的调用模式以确保正确使用。variant 名称的准确性完全依赖 LLM 的代码阅读质量。

**条件 C（Semantic DB）：** 可查询 `trusted.types WHERE module = 'audit.log' AND name = 'ProfileAuditAction'` 获取类型信息；`trusted.functions WHERE module = 'audit.log'` 可确认 `new_event()` 和 `record()` 的当前签名。现有 `trusted.call_graph` 中 `user.profile_service → audit.log` 的调用记录可展示正确的调用模式。

**条件 D（注解 Rust）：** `@nico-type` 注解可能列出枚举的 variant（取决于注解粒度）；`@nico-fn` 提供函数签名。若注解未包含 variant 详情，LLM 仍需阅读 .rs 文件确认。

**已知 LLM 行为风险：**

- 条件 A 下拼错 variant 名（尤其是 `ProfileExport` vs `ProfileExported`），导致编译失败
- 过度响应：修改 `AuditEvent` struct 添加 "export payload"（题目不要求）
- 错误判断 additive enum 变更为 breaking（从而拒绝执行或提出不必要的 migration path）
- 遗漏在 `user.profile_service` 的 spec.interface 中声明新函数的 effects
